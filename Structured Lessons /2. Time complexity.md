## `02_time_complexity/` — How runtime *actually* grows

### First principle (burn this into your head)

Time complexity answers **one question only**:

> As input size `n` grows, how many **operations** does the algorithm perform?

Not seconds.
Not milliseconds.
**Operations.**

An operation is things like:

* comparison
* assignment
* arithmetic
* function call (roughly)

We don’t count them exactly — we **track how they scale**.

---

## The hierarchy you must *feel*, not memorize

```
O(1)        → doesn’t care about input
O(log n)    → input grows, work barely grows
O(n)        → work grows linearly
O(n log n)  → efficient but not trivial
O(n²)       → danger zone
O(2ⁿ)       → death
O(n!)       → instant rejection
```

If your brain doesn’t instinctively panic at `2ⁿ`, you’re not ready yet.

---

## O(1): Constant time (rare, powerful, misunderstood)

```python
def get_first(arr):
    return arr[0]
```

Why O(1)?

* One operation
* No dependency on input size

Even if `arr` has:

* 10 elements
* 10 million elements

This line does **the same work**.

⚠️ Trap:
O(1) does **not** mean “fast”.
It means **unchanging**.

---

## O(n): Linear time (most honest algorithms)

```python
def print_all(arr):
    for x in arr:
        print(x)
```

Operations scale directly with input.

Double the input → double the work.

This is **healthy** complexity.
Most real-world algorithms live here.

---

## O(n²): Nested loops (where bad habits begin)

```python
def pairs(arr):
    for i in arr:
        for j in arr:
            print(i, j)
```

If `n = 1000`
→ operations ≈ **1,000,000**

If `n = 10,000`
→ operations ≈ **100,000,000**

That escalates fast.

Nested loops are not evil —
**unnecessary nested loops are**.

---

## Sequential code ≠ nested code (people mess this up)

```python
for i in range(n):
    pass

for j in range(n):
    pass
```

This is:

```
O(n) + O(n) = O(2n) → O(n)
```

But this:

```python
for i in range(n):
    for j in range(n):
        pass
```

Is:

```
O(n × n) = O(n²)
```

**Add when sequential. Multiply when nested.**
Simple rule. Never forget it.

---

## O(log n): Binary search & controlled growth

```python
def binary_search(arr, target):
    low, high = 0, len(arr) - 1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
```

Each step:

* Cuts input **in half**

That’s logarithmic growth.

This is why:

* Binary search
* Balanced trees
* Divide-and-conquer

Are interviewer favorites.

They show **scaling discipline**.

---

## O(n log n): The “best possible” for many problems

Sorting comparison-based arrays **cannot beat** O(n log n).

Examples:

* Merge sort
* Heap sort
* Tim sort (Python, hybrid)

If you see:

* one loop (n)
* inside a divide-and-conquer (log n)

You’re probably here.

---

## Recursion: where people lie to themselves

### Simple recursion

```python
def sum_n(n):
    if n == 0:
        return 0
    return n + sum_n(n-1)
```

Calls itself `n` times → **O(n)**

### Branching recursion (danger)

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n-1) + fib(n-2)
```

Each call creates **two more calls**.

That’s **O(2ⁿ)**.

If you ever write this in an interview without memoization, you’re done.

---

## Amortized time (advanced but crucial)

Example: Python list append.

```python
arr.append(x)
```

Most of the time: O(1)
Sometimes: expensive resize

But **averaged over many operations** → O(1)

This matters for:

* dynamic arrays
* stacks
* queues

Interviewers love asking this because it separates memorizers from thinkers.

---

## Worst case is king (by default)

When someone asks:

> “What’s the time complexity?”

They mean:

> “Worst-case time complexity”

Unless explicitly stated otherwise.

Best-case answers are **usually irrelevant**.
Average-case only matters if you can **justify distribution**.

---

## How you should analyze *any* code (mental checklist)

1. How many loops?
2. Are they nested or sequential?
3. Does recursion branch?
4. Is input shrinking (log)?
5. Any hidden loops inside library calls?

If you can’t explain complexity **out loud**, you don’t understand it.
