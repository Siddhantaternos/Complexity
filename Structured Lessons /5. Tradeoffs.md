# `05_tradeoffs/` — Choosing under constraints (real engineering)

Knowing time and space complexity is useless unless you can **choose** between options when everything has a cost.

Real systems don’t ask:

> “What’s the fastest algorithm?”

They ask:

> “What survives *these* constraints?”

This folder is about **judgment**.

---

## The core idea (read slowly)

Every algorithm pays a price.

You can trade:

* time for space
* space for time
* simplicity for performance
* predictability for speed

There is **no free optimization**.

---

## Time vs Space: the fundamental trade

### Case 1: Faster time, more memory

```python
seen = set()
for x in arr:
    if x in seen:
        return True
    seen.add(x)
```

Time → O(n)
Space → O(n)

Used when:

* memory is cheap
* speed matters
* input is large

This is common in backend systems and analytics.

---

### Case 2: Less memory, slower time

```python
for i in range(n):
    for j in range(i+1, n):
        if arr[i] == arr[j]:
            return True
```

Time → O(n²)
Space → O(1)

Used when:

* memory is constrained
* input size is small
* environment is limited

This is common in embedded systems.

---

## Why “best” complexity is a lie

The “best” algorithm depends on:

* input size
* memory limits
* latency requirements
* failure tolerance
* maintainability

An O(n) solution that uses huge memory might be worse than O(n²) if `n ≤ 100`.

Context beats theory.

---

## Read-heavy vs write-heavy systems

### Read-heavy

* Databases
* Caches
* Search engines

Optimize for:

* fast lookup
* precomputation
* indexing

Trade-off:

* higher memory
* slower writes

---

### Write-heavy

* Logging systems
* Streaming pipelines

Optimize for:

* append speed
* minimal memory
* batching

Trade-off:

* slower reads
* delayed insights

---

## Precomputation vs on-demand

### Precompute

* Faster queries
* Higher memory cost
* Slower startup

Used in:

* prefix sums
* lookup tables
* caches

---

### On-demand

* Slower queries
* Minimal memory
* Simple logic

Used when:

* queries are rare
* input changes often
* memory is limited

---

## Cache: the most dangerous optimization

Caching improves:

* speed
* latency

But introduces:

* stale data
* invalidation complexity
* memory pressure

Rule of thumb:

> Cache only what you can afford to be wrong about.

---

## When recursion is bad (even if elegant)

Recursion costs:

* stack space
* predictability
* debuggability

Iterative solutions are often:

* safer
* more memory-efficient
* easier to control

Use recursion when:

* depth is guaranteed small
* clarity beats micro-optimization

## Interview-grade decision explanation

When asked:

> “Which solution would you choose?”

Answer like this:

1. State constraints
2. Compare time
3. Compare space
4. Justify choice

Example:

> “Given large input and no memory constraints, I’d choose the O(n) solution using a hash set. It trades extra space for linear time, which is acceptable here.”

That structure matters.

## Real interview traps (read carefully)

### Trap 1: Over-optimizing early

They want correctness first.

### Trap 2: Ignoring constraints

Always ask about limits.

### Trap 3: Saying “it depends” without explaining

Explain *what* it depends on.
